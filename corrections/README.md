# Corrections

Reviewed, human-authored corrections over pipeline output — the escape hatch for
fixes the pipeline cannot make on its own (an over-merge it cannot re-split, a
summary whose source has rolled off the feed and cannot be re-extracted).

`data/` is regenerated by the pipeline and never hand-edited. A correction is the
**only** sanctioned way a human changes a published record, and it is applied by
the pipeline (`pipeline/corrections.py`), not by editing `data/` directly.

## Format

One file per record: `corrections/<record-id>.yml`, validated against
[`../schemas/correction.schema.json`](../schemas/correction.schema.json).

```yaml
record_id: SKS-2026-DL-000003 # required — the record this applies to
author: <name or handle> # required
date: 2026-08-01 # required — YYYY-MM-DD
reason: <one line — why this correction exists> # required
evidence: # optional — citations relied on
  - https://indiankanoon.org/doc/…/
# --- then EITHER quarantine, OR overrides (or both) ---
quarantine: true # route the record OUT of the public site into _review
overrides: # OR: fix specific fields (applied before sanitize)
  status: ACQUITTED
  district: Gurugram
resolution: <optional — how/when this should be retired>
```

## Rules

- Applied **after extraction, before sanitize**, so a corrected value still
  passes every gate (sanitizer, schema, `pii_guard`).
- An override can **never** set a victim-identifying field, an `id`, or
  `minor_involved` — those keys are dropped before the override is applied.
- A corrected record is marked `corrected: true` and shows a **“Corrected”**
  marker on the site; the audit trail is this committed file.
- Adding a correction is a **data change**: it must go through a reviewed PR, the
  same as any change to what the public record says about a real case.

There are currently **no active correction files** — the mechanism ships inert
until an operator authors one.
